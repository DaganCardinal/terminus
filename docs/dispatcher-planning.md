# Planning work with the Dispatcher

The Dispatcher turns a project goal into a persisted proposal of Lines and Stations that you review and explicitly launch.

## Proposing a plan

On a network page, expand **Dispatcher**, describe a project goal, and choose **Propose a plan**. The Dispatcher explores a read-only checkout of the exact saved Terminus commit using its configured harness in a Sandbox. With OpenCode it breaks the goal into focused questions and sends them to OpenCode's read-only `explore` subagents in parallel, then reads the files that decide each Station's boundaries. It cannot edit files, run shell commands, or reach the network. Secret files and Git history are removed before it starts, and repository-supplied OpenCode configuration and instruction files are disabled. Planning takes minutes rather than seconds; the proposal is saved when ready, so the panel can be closed.

Turn on **Check baseline first** in the composer to have orchestration install dependencies and run the project's configured checks on that commit before exploring. Results are trusted context for the Dispatcher and appear on the proposal. If a check fails and the goal doesn't already cover it, the Dispatcher suggests a separate **baseline fix** Line. It is included by default; **Reject fix** removes it. When included, every other Line picks up the accepted fix through a Crossing before its first Station. `PUT /api/networks/NETWORK_ID/plans/PLAN_ID/baseline-fix` with `{ "selection": "include" | "reject" }` makes the same choice.

## Following execution

While planning, the Dispatcher chat shows the real execution phase and a compact activity group. Related observations are grouped into **Workspace preparation**, **Project exploration**, **Proposal checks and corrections**, and **Finishing up**; offline planning has its own **Offline simulation** group. Labels summarize completed file reads, searches, listings, focused explorations and commands. Reported starts and failures are counted separately, because the feed has no invocation identities to correlate starts with completions. Counts describe retained observations, not unique files or whole-run totals. Failures remain visible above the groups even when details are collapsed; they do not by themselves mean the plan failed.

Expand a group for its observations, safe repository-relative paths and timestamps in execution order. **Earlier activity** opens the scrollable history while planning; **Execution activity** keeps it available after the proposal finishes or fails. A group's expansion choice survives new observations and its move into history. Tool observations contain only an allowlisted category, its reported status and, when safe, a repository-relative path. A completed read or exploration is an observation of tool execution, not proof that its conclusions are correct.

New group labels and observations arriving in open live details type out over 450 ms. Restored history, updated counts and tool failures appear immediately. The shared `TypedText` component accepts `durationMs` to tune the total reveal time (zero disables it), and `animate={false}` for immediate text. It respects reduced-motion preferences, exposes complete text to screen readers, and reserves the final text's space. Changed text appears immediately; a new component key starts a fresh reveal.

The shared harness path filters live events inside the Sandbox. Reasoning, assistant prose, search expressions, shell commands, tool arguments/results, task prompts and file contents are never published as activity. Raw harness events stay in the disposable Sandbox for the existing final-outcome parser. Native harnesses use the same normalized protocol; OpenCode reports focused exploration calls, while native command execution is described generically without command text. Child exploration internals are shown only when the harness actually emits them.

Activity is bounded to 200 recent observations from the current planning attempt, retaining its latest phase. D1 batches observations separately from canonical domain events; they cannot drive planning, Train movement or launch. Retries replace the activity attempt and reject late writes from an earlier one. Activity write failures do not fail planning. The browser polls only while the Dispatcher panel and page are visible, catches up after reopening and performs a final history fetch when planning finishes. Offline planning explicitly reports a simulation and never invents repository reads.

`GET /api/networks/:networkId/plans/:planId/activity?after=<seq>` returns `{ attempt, entries, lastSeq, hasMore }`, with at most 100 entries per page. Each entry contains `{ seq, at, activity }`; activity is either `{ kind: "phase", phase }` or `{ kind: "tool", tool, status, path? }`. Continue from `lastSeq` while `hasMore` is true. Replace local history when `attempt` changes. This endpoint checks that the plan belongs to the requested Network and returns `Cache-Control: no-store`.

## Reviewing a proposal

The proposal records **findings**: short facts from exploration with the paths that support them, shown under "What Dispatch explored". They contain no file contents. The backend validates the structured Lines and full Work Manifests and saves the proposal and assessment in D1. Review each Station's scope, expected/avoided areas, contracts, invariants, dependencies, acceptance criteria, and evidence. **Launch Lines** is a separate command; preparing or reopening a proposal does not start Station work. Plans contain at most eight Lines, six Stations per Line, and twenty-four Stations total, including a baseline fix. These limits live in one place, `planLimits` in `packages/protocol/src/dispatch.ts`, which the schemas, the plan tools and the Dispatcher's instructions all read. Model attempts are bounded and never switch models automatically.

With OpenCode, the Dispatcher writes its plan through four plan tools instead of one large JSON answer, so a slip costs one piece rather than the whole proposal. `terminus_set_plan_outline` saves the layout: summary, findings, every Line with its key, name, unload recommendation, ordered Station keys and optional route and `shared` values, any Junctions, which name their Lines by key, and an optional baseline fix, also named by Line key. `terminus_put_station` saves one Station with every Manifest field as its own flat argument (`repositoryChange` becomes `changeKind` and `changeDescription`), so no value nests deeper than a list; several calls may arrive in one message. `terminus_inspect_plan` reports what is saved, what is missing and every known problem. `terminus_finalize_plan` assembles the proposal in code and checks it with the schema and assessment the Workflow uses.

The Sandbox's outbound handler serves the tools as a small remote MCP server inside the Worker (requests never leave Cloudflare) and keeps the draft in D1 (`dispatch_drafts`), one row per outline or Station, so parallel calls never overwrite each other. A Station is refused only when it fails its own schema. Other problems, such as unconfigured evidence, dependency order, or empty invariants after Line-shared values merge, are saved and reported against its key. An outline with any layout problem is refused: keys, where each Line sits, size limits, routes and Crossings, or the baseline fix. Every reply ends with progress: the Stations still missing and where problems remain. GLM sends the outline as JSON text, so it arrives for bracket repair and the precise parse hint; other models send an object. For every model, Station list arguments accept either arrays or text with one item per line (JSON array text also works); `contracts` accepts an array of objects or JSON array text. The same Station tool input schema is included in the Dispatcher prompt, together with a complete call example and an equivalent text-list example. The prompt explains that Manifest fields are flat arguments and `repositoryChange` becomes `changeKind` and `changeDescription`. The server converts text to lists, then applies the full Station schema and assessment; persisted Manifests are unchanged. Plan tool schemas leave out path patterns with lookahead, which some providers cannot compile; the server still checks every value.

Once `terminus_finalize_plan` accepts the plan, the runner beside the harness stops OpenCode, so the session does not spend another model round trip on a closing message. Three consecutive argument-format failures on the same plan tool pause OpenCode early, including malformed calls OpenCode rejects before they reach Terminus. A saved piece or a different failing tool resets that streak; assessment problems do not trigger it. The Dispatcher resumes the same native session with an explicit change of format: one call at a time, flat Station fields, and lists encoded as text. This uses the existing allowance of at most two session corrections, rather than adding retries or switching models. The hard limits of 20 unsaved pieces or 3 rejected finalizations still stop a run. A validation failure at a hard limit reports repeated rejected plan tool calls; exhausted session corrections report three attempts. The saved draft, not the final message, is the answer: the Dispatcher assembles and reviews it exactly as `terminus_finalize_plan` does, so a stopped session needs no closing message. If the harness fails after the saved plan is complete and passes those checks, the plan is kept too. A Sandbox cleanup failure after planning is logged and never discards the result. The checks are advisory: the Workflow validates the proposal again. Apply `0024_dispatch_drafts.sql` before deploying; local Worker development applies it automatically.

A lost stream between the Workflow and its planning Sandbox does not end the session. The streamed command only follows the activity file of a live runner it started detached, so a dropped stream takes down the follower, not OpenCode. The Workflow then follows the same harness again from the last line it handled, in the same container (reattaching never starts one), with up to three attempts over two seconds; only if those fail does the step fail as before, with the lost stream's error. The runner enforces its own time limit, and stops its harness once no follower has touched its heartbeat file for a minute, so a harness never runs on long after the Workflow that started it is gone. A Workflow retry closes the plan's Sandbox before granting any access, so it never prepares beside a harness an earlier attempt left running.

Interrupted attempts retain their draft and a trusted preparation checkpoint in D1 (`dispatch_draft_checkpoints`). The checkpoint binds the repository and exact commit, baseline-check option, validation commands, model and harness execution configuration to the baseline report. A matching Workflow retry rechecks the draft against the current planning context. A complete valid draft returns without repository access or a Sandbox, including when the final proposal commit previously failed. An incomplete or invalid draft starts a fresh session with the saved pieces and the remaining problems; completed baseline checks are reused. Changed preparation configuration, corrupt checkpoint data, or legacy drafts without a checkpoint require fresh preparation and a clean draft. Draft pieces that no longer parse or match their schema read as missing and can be supplied again. Drafts and checkpoints are deleted with their plan or Network. Apply `0025_dispatch_draft_checkpoints.sql` before deploying; local Worker development applies it automatically.

Other harnesses still reply with the proposal JSON. For them, omissions that cannot change a plan are filled in before every check rather than sent back for resubmission: a `null` optional section (`junctions`, `findings`, `baselineFix`) counts as absent, and a missing Manifest `avoidAreas`, `contracts` or `dependencies` is empty. Manifests may carry `projectFacts`, the tooling facts the Dispatcher verified (test environment, setup files, installed libraries), so the Station and Conductor do not rediscover them.

A large plan takes minutes to write: GLM runs at roughly 40–55 output tokens per second. Without plan tools the whole proposal is one response, and one cut off by the output limit is lost and written again from the start; with them, one response may still carry several Stations. The Dispatcher's OpenCode agent therefore gets a 16,384-token output limit (other roles keep 8,192), and its prompt sets a size budget of about 500 tokens per Station. To avoid repeating Line-wide values across a long Line, a Line may carry an optional `shared` object with `avoidAreas`, `invariants`, `expectedEvidence` and `projectFacts`. Before validation, Terminus prepends these to each Station's Manifest on that Line, keeping a repeated value once, and then drops `shared`. Stored proposals and Station Manifests are therefore unchanged, and every Station still needs at least one invariant and one evidence name after the merge. With plan tools, `shared` works on every Line, including Junction and baseline-fix Lines; a proposal written as one JSON object cannot use it on those.

If the proposal still fails schema validation or domain assessment, the field locations and error codes, or the assessment problems, go back into the same native harness session for up to two corrections, so the Dispatcher keeps what it explored. Exhausted schema validation stops Workflow retries and saves safe diagnostics on the failed plan, without raw response values. A proposal that still fails assessment is saved and cannot launch. Transient failures retry the planning step once, reusing matching checkpoints and saved draft pieces for OpenCode. If planning still fails, the plan records only the kind of failure, never the error's own message, which can carry model output or credentials: no agent Sandbox was free, the model or harness configuration is incomplete or changed, the agent stopped before finishing, planning ran out of time, the Sandbox ran out of memory or stopped, or a service was overloaded. Anything else keeps the general message. The step allows 60 minutes, longer than the session's own limits (up to 10 minutes waiting for Sandbox capacity, a 15-minute run and two 5-minute corrections), with 25 minutes left for checkout and baseline checks. This also keeps a retry from overlapping a still-running session in the same named Sandbox. `expectedAreas` and `avoidAreas` contain only plain paths; put explanations, CSS token restrictions, and other prose in scope or invariants instead. `avoidAreas` is a hard boundary for the Station and is usually empty: shared files a Station may need, such as a global stylesheet, go in `expectedAreas`, where overlaps become collision forecasts, with any limits stated in scope or invariants. Path patterns and this guidance are included in the model's JSON schema.

Every newly proposed Station must declare `repositoryChange: { kind, description }`, where `kind` is `implementation`, `tests`, `documentation`, or `configuration`, and the description names concrete repository edits. Running existing checks or confirming earlier features coexist belongs in acceptance criteria and expected evidence, rather than a separate Station. Adding or improving test files is valid work. Final merging and project-wide validation already belong to Terminus integration. Invalid declarations use the existing bounded proposal repair loop. Domain assessment refuses launch without a concrete deliverable, and the Engineer rechecks it before signaling; missing declarations on older waiting Stations block the Train and raise a persisted Dispatcher/user alert. Older plans remain inspectable but must be replanned before launch. A declaration is intent, not proof that the eventual diff will be nonempty; the Conductor still reviews independently collected changes.

## Dependencies and collision forecasts

Code-dependent work must stay on one Line. Dependencies can name only earlier Station keys on that Line; keys are unique across the proposal. Another Line completing a Station does not copy its code into this Train. Contract-based dependencies across planned or active Lines are rejected too. Expected areas use plain repository-relative paths/directories, without globs. Overlaps in declared files/directories or changing contracts are shown as collision forecasts, not stored as Git conflicts. Unknown evidence names or overlaps with avoided areas prevent launch. Forecasting is conservative declared intent; actual diffs, review, and integration checks remain authoritative.

## Launching

Launch requires the reviewed Terminus baseline still to be current. New collision forecasts also require a fresh proposal. Launch forks stable Train repository identities, then records all Lines, Stations, Trains, the plan, and events in one D1 batch guarded against stale canonical state. Only then does it start the individual Train Workflows. Retries reuse saved proposals and identities. Partial repository preparation can leave unused forks in Artifacts, but never a partially laid network. Closing or refreshing the browser does not stop planning or launch.

Each planned Line also carries an unloading recommendation; see [Automatic unloading and human approval](unloading.md).

API clients submit a UUID `requestId` with each new goal. Reuse it when retrying an uncertain submission; reuse with a different goal/network returns 409. The 202 response includes the saved plan; plans and their states also appear in the network snapshot and their changes in the existing event log.

```sh
curl -X POST http://localhost:8787/api/networks/NETWORK_ID/plans \
  -H 'Content-Type: application/json' \
  -d '{"requestId":"64d6315b-7d66-4e50-94aa-4de0b71029ef","goal":"Add an accessible footer and an independent theme toggle, with tests."}'

curl -X POST http://localhost:8787/api/networks/NETWORK_ID/plans/PLAN_ID/launch
```

If a Dispatcher Workflow is `errored` while a plan remains `planning`, `ready`, `launching`, or `starting`, use **Recover interrupted planning/launch** or the retry endpoint. Recovery restarts the same Workflow and reuses any saved proposal/topology. Finished or failed plans need a new request; a stale proposal cannot be launched against newer canonical code.

```sh
curl -X POST http://localhost:8787/api/networks/NETWORK_ID/plans/PLAN_ID/retry
```

## Removing Stations

Waiting or blocked Stations can be removed using **Remove Station** in their details, with a reason, or by posting `{ "reason": "Redundant verification" }` to `/api/networks/NETWORK_ID/stations/STATION_ID/remove`. The deterministic Dispatcher persists the request; the Train Workflow revalidates and applies it. Removal retains the Station as `cancelled` in topology and history, skips it in travel order, and never creates a Car or changes accepted commits. Removing the final Station returns the Train to the Terminus gate. Active/signaled work and accepted Stations cannot be removed. Removal is refused while any unfinished Station, including on another Line, depends on it; cancelled work never satisfies a dependency. Cancel dependents first or explicitly revise the plan. Review blockers belonging to discarded Station work can clear; unrelated conflicts stay blocked and user holds still apply. Lost command wakeups are recovered by periodic gate reads; a request that becomes invalid is recorded as `station.removal_refused` in activity.

Apply `0005_station_removal.sql` before deploying these changes. It protects dependency/removal checks against concurrent topology commands. Local Worker dev applies it automatically; remote migrations use the existing `wrangler d1 migrations apply terminus --remote` command from `apps/worker`.

## Stopping planning

While a goal is being prepared, the composer's Send button becomes **Stop**, including after a refresh. Stop records `dispatcher.plan_cancelled` and a terminal plan with `status: "failed"` and `reason: "cancelled"` (using the existing storage status). The goal and activity remain inspectable. A stopped plan cannot launch or recover; send a fresh goal to plan again.

`POST /api/networks/NETWORK_ID/plans/PLAN_ID/stop` stops only a `planning` plan; another Network's plan returns 404, and a ready or launched plan returns 409. Cancellation is persisted before cleanup. The Worker terminates the Dispatch Workflow and permanently cancels its named planning Sandbox, preventing a concurrent startup or Workflow retry from restarting it. Dispatcher outbound calls run through that Sandbox's existing container adapter, which aborts outstanding fetches and response streams, including primary, utility and hedged AI Gateway requests. Closing the panel alone still leaves planning running.

Late proposals cannot overwrite the cancellation. Stop is idempotent and retries cleanup; if cleanup fails, the endpoint returns 503 with the cancellation retained, and the composer retains Stop for another attempt, including after refresh (`cleanupPending: true`). Successful cleanup clears that flag and records `dispatcher.plan_stopped`. The stopped exchange also offers **Retry stop** after refresh. Abort closes our upstream requests; it cannot promise that the provider immediately stops inference or waives work already billed. Stop does not control Lines already launched.

Planning Sandboxes now use the plan identity instead of a random session identity. Drain planning sessions started by older code before deploying; their random addresses cannot be targeted by this Stop action. Verify a fresh live goal stopped during preparation and streaming, confirm its container shuts down and Gateway requests disconnect, refresh, and submit a new goal. Offline tests use no provider calls.

## Offline planner

The offline environment clearly labels its planner as a simulation: it produces one generic Goal Line, uses fake repositories and checks, and makes no model calls. It exercises the same persisted proposal and launch path. The fixed two-Line demo remains available separately.

## Setup

Planning needs no additional secret: the Dispatcher reuses the existing Gateway credentials. `npm run dev:worker` and `npm run deploy` apply its D1 migrations.
